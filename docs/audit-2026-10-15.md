## Engine

*Scope:* Ledger engine (sharetally/engine/units.py, sharetally/engine/ledger.py) and its tests

*Test run:* Ran from C:\Land Tech: .venv\Scripts\python.exe -m pytest -q tests/test_engine.py tests/test_units.py gave 30 passed in 0.12s. The full suite (pytest -q) gave 51 passed in 1.82s. Five probe and benchmark scripts were also run from the session scratchpad: probe.py, probe2.py, probe3.py, bench.py and bench_seeded.py, in a temporary directory outside the repository. They work on in-memory data only and modified no repository files; the existing .pytest_cache predates this run. They reproduced each weakness listed above.

### ENG-1 — A back-dated proposed deed passes the pre-registration check and pushes an already-registered sale out of priority (high ✔ re-verified)

- **Where:** `sharetally/engine/ledger.py:296-303; sharetally/web.py:581-590,655-657,746`
- **Evidence:** Proposed transfers skip the pre-record filter and are placed by execution_date (ledger.py:296-303). Intake accepts any execution date as long as execution <= registration <= as_of (web.py:581-590). The status shown to the clerk is built only from proposed and plot-wide findings (web.py:655-657; the API does the same at 746). Probe on seeded plot M901-BS-1101: P-0001 proposes '25.00 decimal' with execution 2019-01-01 and registration 2026-09-01. The clerk sees NO_CONFLICT. The full ledger becomes CONFLICT, with OVER_TRANSFER (proposed=False) on the existing DEMO-SRO 2024/0110, and approved case MC-0001 changes to CONFLICT.
- **Impact:** The ante-dated second sale, which is the core double-selling pattern, shows as clean at the one moment a clerk could stop it. If it is saved, the earlier honest buyer is the one flagged. This also contradicts the claim at docs/architecture.md:290 that proposed findings can be separated.

### ENG-2 — The 'already reflected in the khatian' gate uses execution date, not registration date (high ✔ re-verified)

- **Where:** `sharetally/engine/ledger.py:298-302; sharetally/web.py:258`
- **Evidence:** Line 298 turns any transfer with execution_date <= record_date into a 'pre_record' reference row that is never replayed. The UI then labels it 'Before the record date (already reflected)' (web.py:258). Probe: khatian dated 2018-06-30, S holds 10 of 10 decimal. Deed executed 2018-06-20 and registered 2018-08-15, S to A, 10 decimal. Second deed 2019-03-01, S to B, 10 decimal. Result: status ATTENTION (only RECORD_LAG), balances {B: 1}, no OVER_TRANSFER.
- **Impact:** A khatian dated before a deed's registration cannot reflect that deed, so a real double sale ends with no conflict. This is a false negative of the kind the honesty rules exist to prevent.

### ENG-3 — Same-day priority is decided by string order and input order, so balances change with database row order (high)

- **Where:** `sharetally/engine/ledger.py:303,307; sharetally/repository.py:73-74; sharetally/web.py:574; tests/test_engine.py:47-57`
- **Evidence:** The sort key ends with deed_ref compared as a string (ledger.py:303,307), and the stable sort leaves ties in input order. load_plot loads deed items with no ORDER BY (repository.py:73-74). Intake accepts serials of 1 to 6 digits (web.py:574), so '2024/99' and '2024/0100' can both exist. Probe 1: on the same day, 2024/0100 wins and 2024/99 gets OVER_TRANSFER. Probe 2: one deed with two items, S to X and S to Y, 10 decimal each from a 10-decimal holding. In one order the balances are {X: 1}; reversed they are {Y: 1}. The shuffle test (test_engine.py:47-57) cannot catch this because the synthetic data has one item per deed.
- **Impact:** Which buyer is named as the over-transferee depends on zero-padding or row order. No finding says the order could not be determined from the records.

### ENG-4 — Baseline and heir totals ignore the tolerance, so a rounded khatian turns into a plot-wide CONFLICT (high ✔ re-verified)

- **Where:** `sharetally/engine/ledger.py:257,273-281,326,516-517`
- **Evidence:** Line 257 uses hq.value and discards hq.tolerance. Lines 273-281 compare the exact total with 1, and line 326 requires heir_total == 1 exactly. Probes: holdings 16.67/16.67/16.67 decimal on a 50-decimal plot give SHARE_TOTAL_MISMATCH conflict ('5001/5000 (100.02%)'). Three holdings of '.3333 share' give UNALLOCATED_SHARE. Three heirs at '.333 share' give INHERITANCE_SHARES_INCOMPLETE and the inheritance is not applied. SHARE_TOTAL_MISMATCH is in PLOT_WIDE (34-37), and lines 516-517 copy it into every mutation case on the plot.
- **Impact:** Rounding that the engine already forgives in deeds (scenario S16) becomes a CONFLICT on every pending case whenever the khatian itself is written in rounded decimals.

### ENG-10 — The mutation cross-check assumes one item per deed (medium)

- **Where:** `sharetally/engine/ledger.py:452-461,465,480-490`
- **Evidence:** transfers_by_deed = {(office, deed_no): t} keeps only the last item of each deed (465), and the comparison at 480-490 runs against that one item. RECORD_LAG is emitted once per item (452-461). Probe: co-sharers S1 and S2 jointly sell to B in one deed, and a case citing it from S1 gives MUTATION_MISMATCH ['seller'], CONFLICT. The same probe produces two RECORD_LAG findings for the one deed. The schema allows many deed_item rows per deed (db.py:40).
- **Impact:** Once multi-item deeds exist, joint sales by co-heirs (common) produce false conflicts.

### ENG-5 — Over-transfer cascades multiply conflicts and produce false explanations (medium)

- **Where:** `sharetally/engine/ledger.py:391-416,435-440; sharetally/explain.py:145-148; sharetally/web.py:282-283`
- **Evidence:** A partial move (401, 416, 435-440) passes the shortfall on to the buyer. Each later resale gets its own OVER_TRANSFER with subtype 'beyond_recorded_share' (410) and no link to the root finding. A buyer who received 0 is never added to ever_held (440), so that buyer's resale gives NO_RECORDED_SOURCE (391-397), and the explanation says they hold nothing in the deeds (explain.py:145-148) even though a registered deed names them. Probe: S holds 10 of 10 and sells 6 to A, then 6 to B; B sells 6 to C; C sells 6 to E. Result: three conflicts with a 2.00 shortfall each. web.py:282-283 adds up shortfall_dec and shows a 60% overflow, when the real excess is 20%.
- **Impact:** The reviewer sees three apparently independent conflicts and an inflated overflow figure, and some explanation texts are factually wrong.

### ENG-6 — No check for a seller already recorded as deceased; the explanation says they held 0.00 (medium)

- **Where:** `sharetally/engine/ledger.py:303,306,342-343,407,410; sharetally/explain.py:127-128`
- **Evidence:** After an inheritance the deceased's balance is set to 0 (342-343), but nothing is added to outflows. A later sale by the deceased therefore gives OVER_TRANSFER with subtype 'beyond_recorded_share' and held_dec '0.00' (407,410), and explain.py:127-128 renders 'held 0.00 decimal ... more than held'. A sale on the date of death is always ordered after the inheritance (key 0 before 1, lines 303/306). That policy is not documented.
- **Impact:** The engine misses a strong signal (a deed executed in the name of someone the records list as deceased) and gives the reviewer a wrong explanation.

### ENG-7 — Tolerance depends on the unit written, and absorbed shortfalls never become findings (medium)

- **Where:** `sharetally/engine/units.py:113-116,145; sharetally/engine/ledger.py:400,417-421`
- **Evidence:** The tolerance floor of two digits is applied in the raw unit (units.py:116,145). The same 100 decimals gets ±0.5 decimal when written as '1 acre', ±0.005 as '100 decimal' and ±1/87120 decimal as '43560 sqft'. Probe: a seller holding 99.6 of 100 decimal. Selling '1 acre' or '1.00 acre' is applied with rounding_note 0.40 and status ATTENTION. Selling '100 decimal' gives OVER_TRANSFER, CONFLICT. The absorbed shortfall exists only in row.summary (ledger.py:420-421) and never affects the status.
- **Impact:** The same land gets a different verdict depending on the unit. A 0.4-decimal shortfall (about 174 sq ft) per acre-denominated deed passes without notice.

### ENG-8 — deed_type is ignored; legal events the model cannot express either move shares or cannot be entered at all (medium)

- **Where:** `sharetally/engine/ledger.py:52-66,229-234,356-359; sharetally/web.py:578; docs/architecture.md:473`
- **Evidence:** Transfer is a single seller-to-buyer move with a free-text deed_type (ledger.py:52-66), and deed_type is used only in the row summary (359). Probe: a 'mortgage' item moves 100% of the plot to BANK and the status is only ATTENTION. There is no way to express partition (batwara), an atomic exchange, a cancellation or rectification that refers to an earlier deed, a court decree, an attorney acting under a power of attorney, an encumbrance, khas vesting or acquisition, or a dag split or merge (plot area is fixed at 229-234). Intake restricts types to sale and gift (web.py:578), but the engine has no allow-list and no Incomplete code for an event it does not model.
- **Impact:** Any future import or seed path can silently corrupt balances. Real records containing these events will show up as false conflicts instead of Incomplete.

### ENG-9 — One record date per plot, even though holdings carry their own khatian numbers (medium)

- **Where:** `sharetally/engine/ledger.py:120-122,268,298; sharetally/db.py:28`
- **Evidence:** PlotRecord.record_date and record_ref (ledger.py:120-122) apply to every holding (268) and to the pre-record gate (298); the schema stores record_date on the plot table (db.py:28). Probe: khatian 101 (S, 1/2, reissued 2021) and khatian 205 (B, 1/2, opened 2021), plus a 2020 deed S to B for 5 decimal. With record_date 2018, the 2020 deed is replayed again: B ends with 1 and S's legitimate 2024 sale gets a false OVER_TRANSFER. With record_date 2021, the result is correct. The synthetic data always uses one khatian per plot (synthetic.py:85-96).
- **Impact:** Real dags often have several khatians updated at different mutation dates. The engine will either double-count those transfers or miss them.

### ENG-11 — An unresolved plot area silently drops share-denominated transfers (low)

- **Where:** `sharetally/engine/ledger.py:255-257,369-370`
- **Evidence:** The check `if area_dec is None: continue` (369-370) runs before the quantity is parsed, and the row gets no code. Quantities like '1/2 share' need no area, and holdings already handle this case (255-257). Probe: a '2 bigha' plot with no local unit, S holds 1/2 and sells 1/2 twice. Result: INCOMPLETE (UNIT_UNRESOLVED only), both rows not_applied with no codes, and no OVER_TRANSFER.
- **Impact:** A conflict that the records do show is hidden behind Incomplete. The result is still never reported as clean.

### ENG-12 — compute_ledger is monolithic, and the finding catalogue and fact schemas are spread across files (low)

- **Where:** `sharetally/engine/ledger.py:34-37,215-523,337,393; sharetally/evaluation.py:15-17`
- **Evidence:** compute_ledger runs about 309 lines (215-523). Each of roughly 20 add() calls passes the level as a literal. PLOT_WIDE is defined separately (34-37), CODES is repeated in evaluation.py:15-17, and the titles are in explain.py:20-38. Fact keys differ between call sites of the same code: NO_RECORDED_SOURCE uses 'via' at 337 and 'deed_ref' at 393, which explain.py:146 papers over with .get().
- **Impact:** Adding a rule means editing 3-4 files. The rules are harder for both students to explain, and explain.py can fail silently when fact keys drift.

### ENG-13 — OVER_TRANSFER evidence grows quadratically, and ledgers are recomputed on every request (low)

- **Where:** `sharetally/engine/ledger.py:402-413; sharetally/web.py:349-353; sharetally/repository.py:74-77,81-83`
- **Evidence:** Every OVER_TRANSFER copies and formats the seller's full outflow list (402-413). Benchmark, one seller holding n/2 who sells n lots of 1 decimal: n=1000 takes 0.95 s, n=4000 takes 16.3 s, n=8000 takes 66 s (16M 'prior' entries). Valid fan-out with 20k deeds takes 0.42 s. The web layer recomputes every plot on /plots (web.py:349-353), and load_plot makes one extra query per crosswalk lookup and per inheritance's heirs (repository.py:74-77,81-83).
- **Impact:** No effect at demo scale. At pilot scale it is a risk, and a pathological record could stall a worker.

### ENG-14 — Results carry no record of the rules that produced them, and rounded display strings are fed back into arithmetic (low)

- **Where:** `sharetally/engine/ledger.py:25-28,175,242-243; sharetally/web.py:282-283`
- **Evidence:** Ledger stores only engine_version (175), a static '0.1.0' (25). LAG_DAYS and RAPID_DAYS (27-28), the tolerance policy and the sort key are not part of the output. Facts hold rounded strings from as_dec (242-243), and web.py:282 converts shortfall_dec back into a Fraction.
- **Impact:** A stored review cannot show which thresholds and ordering produced its status. UI totals pick up rounding error.

**What the code does today (selected facts):**

- Engine inputs are frozen dataclasses. A Transfer has exactly one seller_id and one buyer_id, plus a free-text deed_type. PlotRecord has a single area_raw, a single record_date and a single record_ref for the whole dag. (`sharetally/engine/ledger.py:43-128`)
- Every quantity is parsed into an exact Fraction. Areas are held in decimals and shares as a fraction of the plot. Anna notation is exact. Katha and bigha raise UnitUnresolved unless the mouza has a local definition. (`sharetally/engine/units.py:33-62,119-152`)
- Tolerance is half a unit in the last stated digit, but never fewer than 2 digits for areas and 4 for shares, and it is counted in the unit as written: _tolerance(digits, 2) * factor. Fractions and anna notation get a tolerance of 0. (`sharetally/engine/units.py:113-116,141-151`)
- The baseline adds up each person's khatian holdings using hq.value and drops the tolerance. A total above 1 gives SHARE_TOTAL_MISMATCH (conflict). A total below 1, or no holdings at all, gives UNALLOCATED_SHARE (incomplete). Both are exact comparisons. (`sharetally/engine/ledger.py:252-284`)
- Any part of the period from record_date to as_of that the registry index does not cover produces a COVERAGE_GAP (incomplete). (`sharetally/engine/ledger.py:192-208,287-291`)
- Event ordering: a non-proposed transfer with execution_date <= record_date becomes a 'pre_record' reference row and is never replayed. Other transfers sort by (execution_date, 1, registration_date, proposed, deed_ref as a string). Inheritances sort by (event_date, 0, ...), so on the same day an inheritance goes first. The sort is stable on that key alone, so ties keep their input order. (`sharetally/engine/ledger.py:294-307`)
- An inheritance is applied only when the heir fractions add up to exactly 1 and the deceased has ever held a share. The deceased's balance is then set to 0 and the estate is split among the heirs. Inheritance inflows also count toward RAPID_RESALE. (`sharetally/engine/ledger.py:312-354`)
- Transfer pipeline, in order: AMBIGUOUS_REFERENCE (skip); area unknown (skip silently); UNIT_UNRESOLVED or INVALID_QUANTITY (skip); NO_RECORDED_SOURCE if the seller never held a share. If share > available + tol, OVER_TRANSFER fires, max(available, 0) moves (a partial move) and the earlier deeds keep priority. Otherwise min(share, available) moves and any shortfall is kept only as row.summary['rounding_note']. (`sharetally/engine/ledger.py:356-445`)
- Balances cannot go negative. Every debit is capped at the available balance, and an inheritance zeroes the deceased's balance. Tolerances cannot pile up in balances for the same reason. The mutation quantity check does add the two tolerances together (c_tol + d_tol). (`sharetally/engine/ledger.py:343,401,418,436,497`)
- RECORD_LAG fires for applied, non-proposed transfers that have no approved mutation after LAG_DAYS=90. RAPID_RESALE fires when the seller acquired a share within RAPID_DAYS=90 by deed or by inheritance. Both are attention level, and both day counts are hard-coded. (`sharetally/engine/ledger.py:27-28,423-433,447-461`)
- Mutation cross-check: a cited deed that is missing from the index gives DEED_NOT_IN_INDEX if the cited date falls inside coverage, otherwise CITED_DEED_UNVERIFIABLE. A cited deed that is found is compared on seller, buyer, date, quantity and plot through transfers_by_deed, which keeps one Transfer per (office, deed_no). Each case's status also includes every plot-wide finding at incomplete level or above. (`sharetally/engine/ledger.py:463-517`)
- compute_ledger is one function of about 309 lines with a nested add() closure. Each call site passes the level as a literal. The PLOT_WIDE set is defined on its own, the code list is repeated in evaluation.CODES, and the titles live in explain.py. (`sharetally/engine/ledger.py:34-37,215-523; sharetally/evaluation.py:15-17; sharetally/explain.py:20-38`)
- The pre-registration check, in both the UI and the API, reports only findings with proposed=True plus plot-wide findings at incomplete level or above. (`sharetally/web.py:655-657,746`)
- Determinism: two runs over all 49 seeded plots gave identical findings, facts and rows (scratchpad probe). The shuffle test compares only status, balances and sorted codes. The synthetic data always has one item per deed and one khatian per plot. (`tests/test_engine.py:47-57; sharetally/synthetic.py:85-109`)
- Docs say priority 'mirrors Transfer of Property Act s.48'. They also already list partition deeds, encumbrances, court orders and cancellations as things the model cannot express. (`docs/architecture.md:288,473`)
- Measured performance: one engine-only pass over the 49 seeded plots takes 4.2 ms, or 7.9 ms including SQLite loading. The /plots page recomputes the ledger for every plot on every request. (`sharetally/web.py:349-353; sharetally/repository.py:65-96`)

## Data and evaluation

*Scope:* Data, storage and evaluation (db.py, repository.py, synthetic.py, evaluation.py, scripts/evaluate.py, scripts/export_dataset.py, plus the write paths in web.py and audit.py that touch storage)

### DATA-1 — Deed items whose plot reference cannot be resolved disappear silently, so missing data reads as clean (high)

- **Where:** `sharetally/repository.py:73-77`
- **Evidence:** load_plot only picks up plot_id-NULL items when _OLD_REF matches and the crosswalk lists this plot (repository.py:74-77); anything else is attached to no plot. The schema allows plot_id NULL with plot_ref '' (db.py:42), and seed() does not validate. Probe on an in-memory copy: inserted items with plot_ref 'R.S. 245' and '' for a holder of BS 1101 selling 50 decimal from a 25-decimal share. No plot loaded either item, and BS 1101 stayed NO_CONFLICT. Intake guards against this (web.py:594), but it saves plot_id NULL whenever plot_ref is given (web.py:679). Editing or deleting a crosswalk row later would therefore make a saved notice vanish.
- **Impact:** This breaks the honesty rule that missing records must yield Incomplete. Organizer samples with old-survey references written differently (dots, Bangla digits, sub-dag forms) would make transfers invisible, including over-sales.

### DATA-2 — Coverage is per mouza, open-ended and blind to the office, and the L.T. notice is not an entity with a received date, which produces false CONFLICT (high ✔ re-verified)

- **Where:** `sharetally/engine/ledger.py:470-478`
- **Evidence:** coverage holds only (mouza_id, source, start, end) (db.py:65-67), and a NULL end becomes date.max (repository.py:90). ledger.py:473 checks only the plot's mouza coverage against basis_deed_date, never m.basis_office. The notice exists only as deed.received_via='lt_notice' with a wall-clock created_at (db.py:37-38, web.py:671-672); there is no notice number, sending office or received_date. Probe: a case citing a deed dated 2026-09-29 (2 days before as_of) that has not been entered yet, and a case citing 'OTHER-SRO 2024/0001', both came out CONFLICT (DEED_NOT_IN_INDEX).
- **Impact:** The engine treats the index as complete up to today. Before a notice arrives, or for any office whose index is not loaded, a legitimate mutation is shown as a conflict when the evidence only supports Incomplete. This is the most likely false positive in a live demo if a judge asks 'what if the notice is late?'.

### DATA-3 — Multi-item deeds collapse in the mutation cross-check, giving a false MUTATION_MISMATCH (high ✔ re-verified)

- **Where:** `sharetally/engine/ledger.py:465`
- **Evidence:** transfers_by_deed = {(t.office, t.deed_no): t for t in plot.transfers} keeps only the last item per deed (ledger.py:465). mutation_case has a single from_id/to_id (db.py:62). Probe: deed 2026/7004 with two items on BS 1230 (co-owners A and B each sell 5 decimal), plus one mutation case per seller. A's case came out CONFLICT with fields ['seller']; B's came out NO_CONFLICT. The generator never makes more than one item per deed (synthetic.py:98-109; probe max items/deed = 1), and intake writes exactly one (web.py:677-679).
- **Impact:** The schema advertises multiple items per deed, but the engine mislabels a common pattern (co-sharers selling together, one deed covering several dags) as a conflict. No test exercises it.

### DATA-4 — The khatian is not an entity, and a dag has one record date even when its khatians were updated at different times (high)

- **Where:** `sharetally/db.py:26-33`
- **Evidence:** holding.khatian_no is free text per row (db.py:31-33), while record_date and record_ref sit on plot (db.py:28). The engine treats every transfer dated on or before plot.record_date as already reflected (ledger.py:298-302) and starts inheritance after it (ledger.py:305). Every synthetic plot has exactly one khatian (synthetic.py:85-96; probe max distinct khatian_no per plot = 1), and record_ref is synthesised as 'BS Khatian {n}' (synthetic.py:90).
- **Impact:** When a dag's shares sit on several khatians and only one was re-issued after a mutation, a single date either counts the reflected transfers again (false OVER_TRANSFER) or drops real ones (false clean). The model cannot be loaded faithfully from per-khatian records.

### DATA-10 — No validated import path for organizer-provided samples (medium)

- **Where:** `sharetally/db.py:121-146`
- **Evidence:** seed() accepts only build_dataset()'s dict. It derives columns from the first row of each list (db.py:124-126) and validates nothing: no date format, quantity readability, reference resolvability or data-origin check. export_dataset.py writes JSON that 'The app does not read' (export_dataset.py:4). There is no CSV reader anywhere. The fictional-name rule exists only in intake (web.py:609-611).
- **Impact:** If organizers supply a sample in the final round, the team has no safe way to load it. Hand-loading it risks DATA-1 and DATA-7 failures live, and there is no record of where the data came from.

### DATA-5 — Deed identity is raw text, so a re-entered notice with different zero-padding is credited twice (medium)

- **Where:** `sharetally/web.py:574-577`
- **Evidence:** UNIQUE (office, deed_no) compares strings (db.py:38). Intake accepts \d{4}/\d{1,6} (web.py:574) and checks duplicates by exact string (web.py:576), so '2024/110' and '2024/0110' are different deeds. Probe: duplicating DEMO-SRO 2024/0110 as '2024/110' on BS 1101 moved the buyer from 10 to 20 decimal and the seller from 15 to 5. The only new finding was ATTENTION/RECORD_LAG. Same-day ordering also falls back to the deed_ref string (ledger.py:303), where '2026/10' sorts before '2026/9'.
- **Impact:** Duplicate L.T. notices, which are realistic when paper and digital intake overlap, inflate balances silently and can hide or invent over-transfers.

### DATA-6 — No history, bitemporality or correction path, and the hash chain does not cover the records themselves (medium)

- **Where:** `sharetally/db.py:73-76`
- **Evidence:** No table has a recorded_at, superseded_by or valid-to column (db.py:26-67). The engine's as_of filters only by real-world dates (ledger.py:296, 305, 467), so a replay 'as of' a past date uses today's knowledge. review stores engine_status and engine_version but no input fingerprint (db.py:73-76, web.py:508-510). No correction endpoint exists; a fix would be an in-place UPDATE. The audit detail for a saved notice is only {plot, engine_status_at_entry} (web.py:681-682), and verify() hashes only audit rows (audit.py:40-49).
- **Impact:** A reviewer's decision cannot be reproduced once later notices arrive. Corrections would destroy the earlier state. Editing deed_item.quantity_raw directly in the DB is undetectable, because there is no baseline hash of the data, only of the log.

### DATA-7 — Missing integrity constraints produce false findings or crashes (medium)

- **Where:** `sharetally/db.py:40-63`
- **Evidence:** Probes on in-memory copies: (a) a duplicate crosswalk row (no PK, db.py:46-48) for a single target gave AMBIGUOUS_REFERENCE with candidates ['M901-BS-1101','M901-BS-1101']. (b) A duplicate heir row (no PK, db.py:54-56) gave heir_total 3/2. (c) record_date '30/06/2018' was accepted (TEXT, no CHECK) and ledger_for raised ValueError (repository.py:16-17); plot_rows computes every plot per request (web.py:351-353), so one bad row breaks /plots. (d) An 'approved' case with NULL decided_date is accepted by the schema and treated as not approved (ledger.py:448-449), giving a spurious RECORD_LAG. Also unchecked: deed_item.mouza_id against the plot's mouza, seller_id <> buyer_id, and plot.survey values.
- **Impact:** Imported or hand-edited data can raise false Incomplete or Attention flags or take a page down. Today only the generator's own discipline prevents this.

### DATA-8 — The audit chain forks under concurrent writes, and data and audit commits are separate (medium ✔ re-verified)

- **Where:** `sharetally/audit.py:28-37`
- **Evidence:** append() does SELECT last hash, then INSERT, then commit, with no BEGIN IMMEDIATE and no UNIQUE(prev_hash) (audit.py:31-36). FastAPI runs the sync routes in a thread pool. Probe on a scratch WAL file DB with 8 threads x 40 appends: verify() returned ok=False at seq 21, and 3 prev_hash values were reused. Intake commits the deed rows (web.py:680) before audit.append (web.py:681); a failure in between leaves an unaudited record.
- **Impact:** Two users acting at once, such as a clerk and a reviewer during the live demo, can make the auditor page report 'chain broken' with no tampering. That undercuts the tamper-evidence claim.

### DATA-9 — No migrations, a stale local DB, and SQLite-specific SQL spread across modules make the PostgreSQL path expensive (medium)

- **Where:** `sharetally/db.py:11-150`
- **Evidence:** CREATE TABLE IF NOT EXISTS never alters an existing table (db.py:11-96), and is_seeded() checks only for a plot row (db.py:149-150). The persistent file data/sharetally.db (config.py:18; present in data/) therefore keeps old schema and data after code changes, while the dashboard scores come from a fresh in-memory copy (web.py:81-89). SQLite-isms: INSERT OR REPLACE (db.py:146), datetime('now') (web.py:509), CAST(dag_no AS INTEGER) for sorting (web.py:349, 563), which errors in PostgreSQL on a non-numeric dag, and positional INSERT VALUES (web.py:668, 677; security.py:37, 77). Roughly 30 raw SQL statements sit in web.py outside repository.py. Missing indexes for queries already in use: inheritance(plot_id) and heir(inheritance_id) (repository.py:81-83), crosswalk(mouza_id, old_survey, old_dag) (repository.py:44), review(case_id) (web.py:328, 479).
- **Impact:** The first schema change will break the students' local demo DB in confusing ways. Moving to PostgreSQL means touching web.py, security.py and audit.py, not one storage module. Performance is fine at demo scale: a probe ran all 3,019 plots in 0.49 s. The bigger issue is that /plots recomputes every ledger on each request, which grows linearly.

### WEB-1 — Blocking work inside async handlers freezes the whole server, including during the live demo (high)

- **Where:** `sharetally/web.py:399-427, sharetally/web.py:488-515, sharetally/web.py:637-685, sharetally/web.py:753-812, sharetally/ai.py:62`

### WEB-2 — Audit appends are not serialized or atomic: concurrent writers fork the chain, and decisions can be stored without an audit row (high ✔ re-verified)

- **Where:** `sharetally/audit.py:28-37, sharetally/web.py:508-514, sharetally/web.py:680-682`

- **Where:** `render.yaml:9-10; sharetally/web.py:360-362,408-422`
- **Evidence:** On Render free the SQLite file, and with it audit_log, reviews and saved L.T. notices, is lost on every restart or sleep (README.md:224). There is no export of the audit head and no backup script. /healthz returns {'ok': True} without opening the DB. With --forwarded-allow-ips="*", uvicorn 0.54 takes the left-most X-Forwarded-For entry (middleware/proxy_headers.py:176-177), so if the edge proxy appends rather than overwrites, the per-IP throttle key and the 'ip' in audit entries are client-controlled.
- **Impact:** The hash chain cannot be demonstrated across restarts, a broken DB would still report healthy, and IP-based throttling and audit detail may be spoofable.

### REPRO-1 — Builds are not reproducible: no lockfile, no Python pin, and an evaluation artefact that changes on every run (medium)

- **Where:** `requirements.txt:1-5; render.yaml:8; README.md:55; scripts/evaluate.py:26; sharetally/evaluation.py:81-82`
- **Evidence:** Only 5 direct pins against about 45 installed packages, with no hashes. Render runs 'pip install -r requirements.txt' on its default Python, since there is no PYTHON_VERSION or .python-version. - **Impact:** A transitive release (starlette, pydantic, httpx2) or a different Python can break the live demo between rounds, and there is no automatic way to show the published evaluation is current.

### TEST-1 — No CI, no coverage measurement, and the AI success paths are untested (medium)

No test stubs the model to exercise draft_notice acceptance, restore(), rejection reasons, the KeyError when 'bn' is missing (it escapes draft_notice, as reproduced), or extract_deed's AI branch. conftest does not clear SHARETALLY_PW_*, SHARETALLY_AS_OF or SHARETALLY_AI_MODEL, so a developer environment can break or change tests (passwords are hard-coded at conftest.py:11-12).
- **Impact:** Regressions in the most judge-visible features (AI fence, Bangla notices) go unnoticed. Nobody knows which branches are covered, and the 'passes on a clean clone' check in docs/team-plan.md:64 is manual.

### TEST-2 — No property-based, browser end-to-end, accessibility or load tests (medium)

### AI-5 — Small robustness gaps in schema and config handling (low)

## Addendum — found during documentation review (15 October 2026)

Three adversarial reviewers checked the new architecture documents against the code. They found these additional issues; the main session reproduced VER-1 and VER-2.

### VER-1 — A case filed after the demo clock is shown as "No conflict" (high, re-verified ✔)

- **Where:** `sharetally/engine/ledger.py:467-468`; `sharetally/web.py:329,478,504,765`
- **Evidence:** `compute_ledger` skips mutation cases with `filed_date > as_of`, so they get no entry in `case_status`. The web layer reads `case_status.get(id, "NO_CONFLICT")`. With `SHARETALLY_AS_OF=2026-08-01`, case MC-0002 (Conflict at the dataset date) shows "No conflict" in the queue, on the case page and in the decision guard, which then accepts "proceed".
- **Impact:** An unevaluated case reads clean, which breaks the "never clean on missing data" rule whenever the demo clock is moved. Fix: a "Not checked" status for cases the engine did not evaluate.

### VER-2 — The clerk's check and the saved ledger can disagree (medium, re-verified ✔)

- **Where:** `sharetally/engine/ledger.py:296-303,443-444`
- **Evidence:** Proposed transfers skip the as-of and record-date filters. On M901-BS-1101 (record date 2018-06-30), a proposal executed 2015-01-01 is replayed as an applied transfer; the same deed saved (not proposed) becomes a `pre_record` reference with no effect. Proposals also never produce `RECORD_LAG`.
- **Impact:** The verdict a clerk sees before saving may not match the stored ledger afterwards. Fix together with F-02 and F-03.

### VER-3 — Deed-text extraction sends party names to the model (medium)

- **Where:** `sharetally/ai.py:228-235`; `sharetally/web.py:791-794`
- **Evidence:** Only `draft_notice` pseudonymises. `extract_deed` sends the clerk's pasted text, names included, inside `<deed_text>` tags whenever a key is set.
- **Impact:** Contradicts any blanket claim that names are tokenised before model calls. On synthetic data this is harmless; with real data it would need a data-protection review or tokenisation before the call.
